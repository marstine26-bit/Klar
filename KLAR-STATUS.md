**Running bug tally this review cycle (2026-09-05 → 09-26): 58 real bugs found and fixed, plus 2 feature gaps closed** across 40 specialist passes.

**40th specialist — Business-mode cloud sync data destruction (2026-09-26, commit `263559d`, live on `main`):** confirmed and fixed a suspicion flagged by the 39th pass — cloud sync predates the Personal/Business mode split and pushed/pulled a single flat blob, so whichever mode was active when the debounced push fired silently overwrote the other mode's data in the cloud (both modes share field names, one row per user). Live-verified: pushing from Business mode after Personal completely destroyed the personal cloud data, and vice versa on the next push. Also found and fixed a cross-mode data leak on pull. Fixed by always pushing both modes' data every sync and routing pulled data to the correct mode on the receiving device. A small note: a disposable test Supabase auth account (`klar-syncaudit-*@mailinator.com`) was created during live-verification and never confirmed/used — safe to delete from Supabase Auth users when convenient, not urgent.

**39th specialist — "Reset Everything" didn't reset everything (2026-09-26, commit `42196d1`, live on `main`):** 2 real bugs found in the local data-erasure flow, which promises "all transactions, accounts, budgets, goals, and settings will be permanently deleted." (1) Business-mode data survived a reset triggered from Personal mode, and vice versa — the two modes live under separate localStorage keys and reset only ever wiped the currently-active one. (2) The PIN lock survived reset entirely (lives outside the app's main data object) — live-verified this is a real trap: resetting with a PIN set leaves the freshly-wiped, empty app permanently locked behind that same PIN, with no way to unlock it short of clearing localStorage via devtools. Both fixed. **Flagged for a future pass**: cloud sync only ever pushes whichever mode is currently active, so Business-mode data likely doesn't reliably round-trip across devices today — a separate issue from this pass's scope.

**38th specialist — AI chat leaking across Personal/Business mode (2026-09-26, commit `919ebe9`, live on `main`):** found and fixed a real privacy bug — `S.chatHistory` was never included in the Personal↔Business data swap, so AI Advisor conversations leaked across the mode boundary in both directions, both visibly in the transcript and as actual context sent to Groq. Live-verified: a personal-mode chat message survived a switch to Business mode intact. Fixed by adding `chatHistory` to the swap list and clearing the transcript DOM on mode toggle.

**37th specialist — CSV import robustness (2026-09-26, commit `6029da4`, live on `main`):** 2 real bugs found and fixed. European bank-export CSVs using comma as a decimal separator (e.g. "45,32") were silently inflated ~100x on import (became 4532) — the parser assumed commas were always thousands separators. Fixed with a `parseAmt()` helper that detects the actual convention per value. Also fixed: large imports (tested 50,000 rows) froze the tab for ~10 seconds with zero feedback, looking crashed — now processes in chunks with a live "Importing N transactions…" indicator. **The multi-currency transaction-aggregation issue flagged by the 34th pass is now fully closed** — 97 call sites across Trends, Budget, Cash Flow Forecast, Goals/Debts, Insights, AI chat/summaries, and tax auto-fill all correctly convert foreign-currency transactions before summing, confirmed by two exhaustive grep sweeps finding no remaining cross-account raw-`t.amount` sites.

**36th specialist — completed the currency-aggregation sweep (2026-09-26, commit `c0973ec`, live on `main`):** went through every remaining site from the 34th/35th passes' flagged list, live-verifying each. Found and fixed a second distinct bug along the way: Cash Flow Forecast's "Current Balance" was a hand-rolled sum that ignored both transfers and foreign-currency accounts (not just currency) — replaced with the same `calcAccBalance()`+`zarRate` pattern Net Worth already uses correctly.

**35th specialist — cross-account currency conversion for income/expense sums (2026-09-26, commit `ac7ad42`, live on `main`):** follow-up to the 34th pass. Added a `txnAmtLocal(t)` helper (mirrors the existing account-balance conversion convention) and applied it at the highest-impact sites: `avgInc()`/`avgExp()` (30+ callers app-wide), Dashboard KPIs, KPI sparklines, Cash Flow chart, and Savings Rate page. Live-verified a $1,000 USD transaction correctly converts to R18,500 in the Income KPI instead of showing R1,000 raw. **Deliberately scoped down** — Trends/Budget-actuals/Forecast/goal-debt-contribution sums still use raw amounts and are flagged for a dedicated follow-up pass, now trivial since `txnAmtLocal` exists as a ready-made primitive.

**34th specialist — account-currency display bugs (2026-09-26, commit `852cad9`, live on `main`):** 3 real bugs found where a foreign-currency account's balance was shown/summed raw instead of converted via `zarRate`, most notably the Dashboard's "Total Balance" hero KPI — the single most prominent number in the app — which ignored FX conversion entirely (a $250 account showed as -R250.00 instead of the correct -R4,625.00 at an 18.5 rate). Also fixed the Accounts page summary row and Net Worth's account cards, both of which disagreed with their own already-correct totals. **Flagged for a future dedicated pass** (larger scope): Dashboard income/expense/savings-rate KPIs and several forecast/budget functions sum transaction amounts across accounts with zero currency conversion — a deeper multi-currency aggregation issue, not just a display bug.

**33rd specialist — category management (2026-09-26, commit `2b4d369`, live on `main`):** custom-category creation was unreachable from every primary entry point (Add Transaction, Set Budget, Edit Recurring Template) — the `__new_cat__` sentinel option was only ever added to the transaction list's inline quick-edit dropdown. Custom categories also had no way to be renamed or deleted once created. Fixed both: creation is now reachable from all 3 relevant selects, and a new edit/delete management list handles rename (updates everywhere via the shared `CATS` array) and delete (reassigns affected transactions/templates to "Other", cleans up budgets/rules, never silently deletes spending history). Also fixed a general bug found as a byproduct: `klConfirm()`/`klPrompt()` dialogs were invisible when opened from inside an already-open modal (equal z-index, DOM order lost) — a previously-unreached stacking bug that would have hit any future nested-confirm feature.

**32nd specialist — recurring template editing (2026-09-26, commit `450d659`, live on `main`):** recurring transaction templates had no way to be edited — only Pause/Resume and Delete existed, so fixing a wrong amount or category meant delete-and-recreate (losing history). Added an Edit button and modal, matching the app's established category/account-select population pattern. Explicitly only affects future postings; already-posted transactions are untouched.

**31st specialist — receipt attachments silently discarded on edit (2026-09-26, commit `d9c7aae`, live on `main`):** found and fixed a real, live-verified bug — the receipt-photo feature was completely non-functional on the edit path. `openEditTxn()` always cleared the receipt UI even when a receipt already existed, and `saveTxn()`'s edit branch never wrote the receipt back to the transaction at all. Net effect: editing a transaction with a receipt looked like data loss, replacing a receipt silently kept the old one, attaching one for the first time via edit did nothing, and removing one had no effect. Fixed so add/replace/remove during edit all persist correctly.

**30th specialist — currency-lock corruption + CIT/Trust calculator bugs (2026-09-26, commit `0e16b75`, live on `main`):** found and fixed a serious bug — repeatedly switching region on an empty account could permanently lock `dataCurrency` to a stale value, causing every number app-wide (including calculator inputs) to be silently multiplied by a live FX rate forever (reproduced a ~21.7x inflation). Also fixed: the CIT calculator's "Key Corporate Tax Dates" card was permanently empty (dead UI, no function ever wrote to it), and Trust Tax's result note always said "Type A" regardless of which Special Trust type was selected.

**29th specialist — Vehicle Costs / Medical Gap tracker bugs (2026-09-25, commit `09e0a11`, live on `main`):** 3 real bugs found and fixed. Vehicle Costs double-counted any petrol transaction imported via the auto-detected-fill-up banner (R500 fill-up showed as R1,000 total). MedGap's "Unclaimed" stat tile lied when a claim exceeded out-of-pocket cost, still showing "Unclaimed" with a positive number instead of flipping to "Overclaimed". `delMedGap`'s confirmation dialog checked a non-existent field name (`e.desc` vs the real `e.description`), so it always showed the generic fallback message.

**28th specialist — dead USD-holdings feature + 2 FX math bugs (2026-09-25, commit `26e87e8`, live on `main`):** the Retirement → FX tab's "USD Holdings" tracker was permanently dead for every user — it filtered holdings by a `currency` field the Add Holding modal had no way to ever set. Making it reachable (added a Currency field) surfaced 2 more real bugs: the UK branch computed the reciprocal of the GBP/USD rate (would have overstated USD holdings by ~60%), and a first-fix attempt double-converted currency before `fmt()`'s own conversion ran. Also fixed: the FX widget's card title stayed stuck on "GBP/USD" after switching region UK→SA.

**27th specialist — transfer type-change left money double-counted or vanished (2026-09-25, commit `16294bd`, live on `main`):** follow-up to the 26th pass's deletion fix, checking the same bug class in editing. Changing a transaction's type to/from 'transfer' never touched the paired leg: converting a transfer leg to expense/income double-counted the money (new expense on one side, untouched transfer-in still standing on the other); converting an expense/income to transfer created no paired leg at all, silently vanishing the amount from the source account. Fixed both directions to cascade the paired leg correctly, matching the deletion fix's convention.

**26th specialist — transfer deletion left orphaned/phantom balances (2026-09-25, commit `feae9e7`, live on `main`):** 3 real bugs found and fixed, all in how the app deletes a transfer's two paired transaction rows (linked via `linkedId`). `delTxn` and `bulkDelete` could each delete just one leg, leaving the other account with a phantom balance and no matching entry. `delAccount` was worse — deleting an account with a transfer to/from a surviving account left that account permanently stuck with money that traces to nothing. Fixed all three to always cascade to both legs together.

**25th specialist — subscription auto-detection amount/cycle bugs (2026-09-25, commit `e4f0c28`, live on `main`):** 2 real bugs found and fixed. (1) `detectSubscriptions()` used the last-pushed transaction's amount instead of the chronologically-last one, silently understating price increases forever once a detected subscription was added. (2) `toMo()` had no `fortnightly` branch, so a real fortnightly subscription was treated as monthly everywhere its cost rolled up (Subscriptions tiles, Cash Flow Forecast, notifications, health-score) — roughly halving its true monthly cost.

**24th specialist — PIN lock never engages on fresh load (2026-09-25, commit `4e48b7d`, live on `main`):** found and fixed a real, live-verified bug that defeated the entire point of the PIN lock feature (Settings → "Enable PIN lock"). The lock was only ever triggered by a `visibilitychange` listener that starts a 60-second background timer — it was never checked on page load. Live-verified: with a PIN set and enabled, a full page reload, a brand-new tab to the same URL, or reopening a closed tab all loaded straight into the dashboard with real account balances and transactions visible — no PIN prompt at all. The only way the lock ever actually appeared was leaving the *same still-open tab* backgrounded for a full uninterrupted 60 seconds, which doesn't cover the realistic "someone else picks up the device" threat model at all. Fixed by adding a synchronous inline check (right after the `#kl-pin-lock` element, before any later script renders real data) that shows the lock immediately whenever `kl_pin_enabled`/`kl_pin_hash` are set in `localStorage`, plus a `pageshow` handler that re-checks on back-forward-cache restores (e.g. unlock → navigate away → hit Back could otherwise restore the already-unlocked DOM without re-running any script). Verified live: fresh load now shows the lock screen immediately with real data never painted first; correct PIN still unlocks normally; wrong PIN still shows "Incorrect PIN. Try again." and stays locked; PIN-disabled accounts see no change in behavior. Not fixed (lower priority, flagging for a product decision, not a bug): no attempt-limiting/lockout on wrong PIN guesses (4-digit PIN, unlimited tries) — the code already comments that the hash is "good enough for local PIN (not a security key)," so this may be an accepted tradeoff rather than an oversight.

**23rd specialist — Split Bills settlement corruption (2026-09-25, commit `726007f`, live on `main`):** found and fixed a real, live-verified bug — removing a group participant still linked to an expense (as payer or split-participant) silently corrupted the settlement math: removing the payer of an expense made its cost vanish from the settlement entirely, and once that dangling reference existed, the greedy settlement algorithm produced phantom transfers between people who never shared an expense while dropping someone else's real debt. Fixed by blocking removal with an error toast while the person is still linked to any expense.

**22nd specialist — cross-tab data loss (2026-09-25, commit `8601bba`, live on `main`):** found and fixed a real, live-verified data-loss bug — the app had zero cross-tab awareness. Each tab loads `S` once at page-load and `save()` always does a blind overwrite of `localStorage`, so with two tabs open, whichever tab saves last silently wins and the other tab's already-persisted edits vanish with no warning. This affects every user (guest/free-tier included), unlike the cloud-sync path which already has real conflict handling but only for signed-in Essential+ users across devices. Fixed with a `storage` event listener that warns the stale tab to refresh before editing (deliberately no auto-merge — no trustworthy ordering exists for two same-device tabs the way there is for cloud sync's server-assigned versions).

**21st specialist — goal/debt ↔ transaction sync reconciliation (2026-09-24, commit `3cf6dfa`, live on `main`):** 2 real bugs found and fixed in `syncConnectedData()`. (1) Manual goal contributions ("+Add", surplus allocation) were silently discarded once a goal had any linked transaction — the sync engine recomputed `saved` from `originalSaved + linkedTxnTotal` on every `renderAll()`, wiping out manual additions that never touched `originalSaved`. (2) Deleting the last transaction linked to a goal or debt left `saved`/`balance` permanently stuck instead of reverting to baseline — the recompute only ran when the linked total was `>0`. Fixed both by keeping `originalSaved` in step with manual mutations and always running the recompute when a baseline exists.

**20th specialist — search/filter/sort correctness (2026-09-24, commit `ec14f5e`, live on `main`):** 2 real bugs found and fixed, both live-verified. (1) Tags view's "click a #tag chip to filter" was completely broken — the search filter never checked the `t.tags` array field, only description/note/amount/category, so clicking a tag chip on a transaction with no textual overlap returned 0 results. (2) Merchants view silently hard-capped at the top 100 entries with no pagination, while the header count showed the true total — a user with 121+ distinct merchants had 21+ permanently inaccessible with no indication anything was hidden. Fixed by adding pagination matching the existing `renderTxns`/`TXN_PAGE` convention.

**19th specialist — month-overflow date drift (2026-09-24, commit `f70bba4`, live on `main`):** found a real, live-verified bug in recurring-transaction/subscription/reminder date advancement — native `Date.setMonth()` silently overflows into the next month when the current day doesn't exist there (Jan 31 + 1 month → Mar 3, skipping Feb). This caused permanent drift: a recurring template anchored on the 31st, after crossing a Feb boundary once, would keep firing on the 3rd of every month forever. Fixed with a shared `addMonthsClamped()` helper (clamps to the target month's last day, the standard billing-system approach) across `checkRecurringDue`, `skipRecurring`, `advanceSubDate`, `doneReminder`, and the debt-payoff calculator's month-label projection.
